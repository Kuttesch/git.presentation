Origins: The BitKeeper Crisis

2005: A Critical Turning Point

Before Git, the Linux Kernel team used a proprietary VCS called BitKeeper. In April 2005, a copyright dispute caused the free license to be revoked.

  • The Linux community needed a new home immediately.
  • Existing open-source options (CVS, Subversion) were too slow for the massive Kernel project.
  • The requirement: A distributed system that could handle thousands of patches efficiently.

Torvalds' Solution

"I did it in ten days"

Linus Torvalds, the creator of Linux, disappeared for a week and emerged with Git.

"I want to be able to apply patches in three seconds, not three minutes."

His core design philosophy:

  • Speed: Performance was non-negotiable.
  • Distributed: Every developer has the full history.
  • Data Integrity: Cryptographically secure history (SHA-1).

What's in a Name?

The Information Manager from Hell

Linus has a dry sense of humor. He famously quipped: "I'm an egotistical bastard, and I name all my projects after myself. First 'Linux', now 'git'."

The name "git" is British slang for an unpleasant or contemptible person.

The original README file listed multiple definitions, ranging from "random three-letter combination" to "goddamn idiotic truckload of sh*t".

"git" can mean anything, depending on your mood. - random three-letter combination that is pronounceable, and not actually used by any common UNIX command. The fact that it is a mispronunciation of "get" may or may not be relevant. - stupid. contemptible and despicable. simple. Take your pick from the dictionary of slang. - "global information tracker": you're in a good mood, and it actually works for you. Angels sing, and a light suddenly fills the room. - "goddamn idiotic truckload of sh*t": when it breaks.

The Git Data Model

Three States of a File

Understanding where your code lives is key to avoiding mistakes.

  • Working Directory: Your active file system where you edit code.
  • Staging Area (Index): A preview of your next commit.
  • Repository (.git): The permanent history of your project.

Files move from Working → Staging → Repository.

Essential Setup & Context

Command Description Context
git init Initialize a new git repository locally. Starting fresh.
git clone <url> Download a repository from a remote source. Onboarding.
git status Show the working tree status. Your daily check-up.
git switch <branch> Switch to a specific branch. Navigation.
git fetch Download objects and refs from another repository. Safe update (no merge).

Action & Sync Toolkit

Command Description Context
git add <file> Add file contents to the index (Staging). Prepare commit.
git rm <file> Remove files from the working tree and index. Deletion.
git commit -m "msg" Record changes to the repository. Save point.
git pull Fetch from and integrate with another repo. Fetch + Merge.
git push Update remote refs along with associated objects. Publishing work.

The Daily Workflow Cycle

# 1. Check what changed
$ git status
modified: style.css
deleted: old_script.js

# 2. Stage changes (Add/Remove)
$ git add style.css
$ git rm old_script.js

# 3. Commit snapshot
$ git commit -m "refactor: update styles and cleanup"

# 4. Sync with team
$ git fetch
$ git pull
$ git push origin main

The Cycle

  1. Inspect: Always start with status to know where you stand.
  2. Stage: Select exactly what goes into the next snapshot using add, rm, or mv.
  3. Commit: Seal the snapshot with a meaningful message.
  4. Sync:
    • fetch to see what's new safely.
    • pull to merge those updates.
    • push to share your work.

Scenario A: Cloning an Existing Repo

Getting Started Quickly

When you join an existing project, you rarely start from scratch. You download the history from a server (GitHub, GitLab, etc.).

  • Clone: Downloads the entire history and checks out the default branch.
  • Remote: The source is automatically saved as the remote named origin.
# 1. Copy the SSH URL from GitHub/GitLab
$ git clone git@github.com:user/project.git
Cloning into 'project'...
remote: Enumerating objects: 105, done.
Receiving objects: 100% (105/105), 12.4 KiB, done.

# 2. Go into the folder
$ cd project

# 3. Verify connection
$ git remote -v
origin git@github.com:user/project.git (fetch)
origin git@github.com:user/project.git (push)

First Time Setup

Identify Yourself

Git will not let you commit until you tell it who you are. This information is baked into every commit you make forever.

  • User Name: Appears in the log and on GitHub/GitLab.
  • Email: Must match your GitHub account to link commits to your profile.
  • Editor: Defaults to Vim (which can be scary). Change it to Nano or VS Code if you prefer.
# 1. Set Name
$ git config --global user.name "John Doe"

# 2. Set Email
$ git config --global user.email "john@example.com"

# 3. (Optional) Set Editor to VS Code
$ git config --global core.editor "code --wait"

# 4. Check settings
$ git config --list

Scenario B: Starting from Scratch

# 1. Initialize Git in current folder
$ git init
Initialized empty Git repository in /app/.git/

# 2. Create a file
$ echo "# New Project" >> README.md

# 3. Stage & Commit
$ git add README.md
$ git commit -m "feat: initial commit"

# 4. Link to GitHub (add remote via SSH)
$ git remote add origin git@github.com:user/repo.git

# 5. Push (set upstream)
$ git push -u origin main

The "New Project" Run

  1. Init: Transforms the current folder into a Git repo (creates hidden .git folder).
  2. Create: Make your first file (usually README).
  3. Commit: Save the first snapshot locally.
  4. Remote Add: Tell Git where the server lives (alias it as origin).
  5. Push -u: Push the code and tie your local branch to the remote one (tracking).

The .gitignore File

"What happens in the repo, stays in the repo..."

Unless it is ignored. This file tells Git which files to intentionally track and which to ignore.

  • Dependencies: node_modules/, /vendor
  • Secrets: .env, api_keys.txt
  • Build Artifacts: /dist, /build, *.log
  • System Files: .DS_Store

Important: If you already committed a file, adding it to .gitignore later won't remove it from history.

# .gitignore content example
# Dependencies
node_modules/
*.log

# Secrets (Never commit these!)
.env
private_key.pem

# OS junk
.DS_Store
Thumbs.db

The Power of Branching

A branch in Git is simply a lightweight movable pointer to a commit.

HEAD -> feature/login
|
[Commit C] -> [Commit B] -> [Commit A]

Why Branch?

  • Isolation: Develop features without breaking production.
  • Context Switching: Pause work and fix a bug elsewhere easily.
  • Experimentation: Try ideas safely; delete the branch if they fail.

Feature Branch Workflow

The standard industry workflow for collaboration.

  1. Update: Ensure local main is up to date.
  2. Branch: Create feature/xyz to isolate work.
  3. Commit: Make granular, logical commits.
  4. Push: Upload branch to remote.
  5. PR: Open Pull Request for review.
# 1. Update Main
$ git checkout main
$ git pull

# 2. Create Branch
$ git checkout -b feature/login-page
Switched to a new branch 'feature/login-page'

# 3. Work & Commit
$ git add login.html
$ git commit -m "feat: add login form"

# 4. Push
$ git push -u origin feature/login-page

Git Stash (The "Pause" Button)

Scenario: The Boss Interruption

You are deep in messy code on feature/login. Your boss rushes in: "Production is down! Fix it on main now!"

You can't commit (code is broken). You can't switch branches (git forbids it with dirty state).

Solution: git stash takes your dirty state, saves it on a clipboard, and reverts your working directory to the last clean commit.

# 1. Save messy work to clipboard
$ git stash
Saved working directory and index state WIP...

# 2. Go fix the bug
$ git checkout main
$ ... (fix bug, commit, push) ...

# 3. Return and restore work
$ git checkout feature/login
$ git stash pop
On branch feature/login... Changes to be committed...

Collaboration & Code Review

The Pull Request (PR) Lifecycle

Collaboration happens before the merge.

  • Code Review: Peers check logic, style, and bugs.
  • CI/CD Checks: Automated tests run against your branch.
  • Discussion: Resolving comments and iterating.
  • Approval: Explicit sign-off required to merge.

Git Tags (Releases)

Marking Milestones

While branches move with every commit, tags are permanent bookmarks in history. They are used to mark specific versions of your software (e.g., v1.0, v2.0).

  • Annotated Tags: Store the tagger's name, email, date, and a message. Recommended for releases.
  • Lightweight Tags: Just a name pointing to a commit.
# 1. Create an annotated tag
$ git tag -a v1.0.0 -m "Release version 1.0"

# 2. List tags
$ git tag
v1.0.0
v0.9.0

# 3. Push tags to remote
$ git push --tags
Total 0 (delta 0), reused 0 (delta 0)
To git@github.com:user/repo.git
* [new tag] v1.0.0 -> v1.0.0

Merge vs. Rebase

Merge (Non-Destructive)

Creates a "merge commit". Preserves history exactly as it happened. Good for public branches.

Rebase (Destructive/Rewrite)

Moves your entire branch to begin at the tip of the main branch. Creates a linear history. Cleaner history, but dangerous on shared branches.

Never rebase a public branch others rely on!

Resolving Merge Conflicts

When Git Gets Confused

If two people edit the exact same lines of the same file, Git cannot automatically merge them. It pauses and asks for help.

The Process:

  1. Open the file in your editor.
  2. Look for <<<<<<< markers.
  3. Edit the code to how it should look.
  4. Remove the markers.
  5. git add the file and git commit.
$ git merge feature/update-header
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and commit.

<<<<<<< HEAD
<h1>Welcome to My Site</h1>
=======
<h1>Welcome to Our Amazing App</h1>
>>>>>>> feature/update-header

Undoing Mistakes

Git Reset (Destructive)

Rewinds history to a previous state.

git reset --hard HEAD~1

  • Use when: You made a mistake locally and haven't pushed yet.
  • Effect: The bad commit disappears. It never happened.

Git Revert (Safe)

Creates a new commit that is the exact opposite of the bad commit.

git revert <commit-hash>

  • Use when: You already pushed the bad code to a shared branch.
  • Effect: History is preserved, but the bug is fixed safely.

The Reflog: Your Safety Net

"I deleted my branch! It's gone forever!"

No, it's probably not.

Git keeps a hidden log of every movement of the HEAD pointer (commits, resets, merges, branch switches) for 30-90 days.

If you reset --hard to the wrong place, you can find the "lost" commit hash in the reflog and reset back to it.

$ git reflog
ea32c11 HEAD@{0}: commit: Fix login bug
4b8d920 HEAD@{1}: reset: moving to HEAD~2
92a4b11 HEAD@{2}: checkout: moving from main to feature

# Recover the state before the reset:
$ git reset --hard 92a4b11

Visualizing History (Log)

$ git log --oneline --graph --all
* a1b2c3d (HEAD -> main) Fix styling
* e4f5g6h Merge branch 'feature/auth'
| \
| * 7h8i9j0 (feature/auth) Add login form
| * k1l2m3n Update user model
* /
* o4p5q6r Initial commit

Don't Fly Blind

The standard git log is verbose and hard to read. Use flags to see the "subway map" of your repository.

  • --oneline: Compress each commit to one line.
  • --graph: Draw the branch structure using ASCII art.
  • --all: Show all branches, not just the current one.

Tip: Alias this command to `git lg` in your config!

Interactive Rebase (git rebase -i)

What is it?

A powerful tool to polish your commit history before merging. It lets you edit commits that have already been made (but not pushed to a shared/locked branch).

Why use it?

  • Fix typos in commit messages.
  • Combine (squash) multiple "WIP" commits into one.
  • Delete unwanted commits.
  • Reorder commits for logical flow.
$ git rebase -i HEAD~3

# Opens your editor with a list of commits...

Interactive Rebase Commands

Keyword Effect
pick Use the commit as is (default).
reword Use the commit, but edit the commit message.
edit Use commit, but stop for amending (changing content).
squash Use commit, but meld into previous commit.
fixup Like "squash", but discard this commit's log message.
drop Remove commit.

Git Best Practices

  • Atomic Commits: One commit should do one thing. If you fix a bug and add a feature, that's two commits.
  • Good Messages: Subject line < 50 chars. Imperative mood ("Add login", not "Added login").
  • Review Culture: Don't just approve. Ask questions. Code reviews are for knowledge sharing.
  • Don't Rewrite Public History: If you've pushed to `main`, don't rebase it.
